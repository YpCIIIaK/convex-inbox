# Как устроен Property Inbox — разбор для себя

Этот файл объясняет проект целиком: что где лежит, как фронт общается с бэком, почему сделано именно так.
Прочитай перед собеседованием — по нему можно уверенно рассказать про любую часть.

---

## 1. Общая картина

```
 Браузер (React + Vite)                         Convex (бэкенд в облаке или локально)
 ─────────────────────                          ──────────────────────────────────────
 useQuery(api.conversations.list)  ◄── WebSocket ──  query      — читает БД, реактивно
 useMutation(api.conversations.send) ──────────►     mutation   — пишет в БД, транзакция
                                                    action      — внешний мир (fetch к OpenRouter)
 fetch(uploadUrl, file) ───────────────────────►    file storage
                                                    scheduler   — запуск функций в фоне
 curl POST /inbound ───────────────────────────►    httpAction  — вебхук
```

Главная идея Convex: **бэкенд — это просто TypeScript-функции в папке `convex/`**. Нет отдельного сервера,
нет REST-роутов, нет ORM. Схема БД тоже на TypeScript (`convex/schema.ts`), и из неё генерируются типы,
которые фронт использует напрямую (`convex/_generated/api`). Поменял аргументы функции — фронт сразу
подсветит ошибку типов.

---

## 2. Три вида функций — это ключ ко всему

| Тип | Что может | Чего не может | Пример в проекте |
|---|---|---|---|
| **query** | читать БД | писать, делать fetch | `conversations.list`, `tickets.board` |
| **mutation** | читать и писать БД, ставить задачи в scheduler | fetch наружу | `conversations.send`, `imports.start` |
| **action** | fetch наружу, вызывать query/mutation через `ctx.runQuery/runMutation` | напрямую трогать `ctx.db` | `agent.run`, `imports.run` |

- **Query реактивные.** Фронт подписывается через `useQuery`, и когда данные в БД меняются, Convex сам
  пересчитывает запрос и пушит результат по WebSocket. Поэтому в проекте нет ни одного «обнови список» —
  отправил сообщение, и список слева, счётчики во вкладках, доска заявок обновились сами.
- **Mutation — транзакция.** Всё внутри либо применяется целиком, либо откатывается. Convex сам повторяет
  мутацию при конфликте, поэтому она должна быть детерминированной (нельзя fetch, нельзя `Math.random` для логики).
- **Action — для внешнего мира.** Не транзакция. Поэтому агент (fetch к OpenRouter) и разбор CSV живут в action,
  а каждую запись в БД они делают через маленькую `internalMutation`.
- **internal*** функции (`internalQuery`, `internalMutation`, `internalAction`) нельзя вызвать с фронта — только
  с сервера. Так закрыты опасные операции: вставка пачки жильцов, привязка тенанта агентом и т.п.

## 3. Данные (`convex/schema.ts`)

```
properties ─< units ─< tenants ─< conversations ─< messages
                                       │
                                       ├─< tickets
                                       └─< agentRuns (шаги агента)
imports (прогресс импорта CSV)
```

Индексы — это то, через что быстро ищем (Convex не даёт сканировать таблицы без индекса в «правильном» коде):

- `conversations.by_status_last` — вкладки Open/Pending/Closed, сортировка по последнему сообщению.
- `conversations.by_tenant_channel` — найти последнюю переписку жильца в нужном канале (для входящих).
- `tenants.by_email` — сопоставить отправителя с жильцом; дедупликация при импорте.
- `tenants.search_name` — **полнотекстовый** поиск по имени (страница Tenants и инструмент агента).
- `tickets.by_status` — колонки доски.

## 4. Фронтенд (`src/`)

- `main.tsx` — создаёт `ConvexReactClient` с URL из `.env.local` (`VITE_CONVEX_URL`) и оборачивает приложение в `ConvexProvider`.
- `App.tsx` — шапка с тремя разделами (Inbox / Tenants / Tickets), кнопки «Simulate inbound» и «Import tenants».
  Роутера нет специально: три экрана, хватает `useState`.
- `components/ConversationList.tsx` — `useQuery(api.conversations.list, { status })`.
- `components/Thread.tsx` — переписка, смена статуса, ручная заявка, ответ, запуск агента.
  **Оптимистичное обновление:** `useMutation(...).withOptimisticUpdate(...)` — сообщение сразу дописывается
  в локальный кэш запроса `conversations.get`, поэтому появляется мгновенно (≈50 мс в тесте), а когда сервер
  подтвердит, Convex заменит его настоящей записью. Если мутация упадёт — откатит.
- `components/TenantsView.tsx` — `usePaginatedQuery` + поиск. `useDeferredValue` не даёт дёргать сервер на каждую букву.
- `components/TicketsView.tsx` — доска из трёх колонок, стрелками двигаем статус.
- `components/ImportDialog.tsx` — загрузка CSV и прогресс-бар (прогресс = обычный реактивный query по таблице `imports`).
- `components/SimulateDialog.tsx` — «написать от имени жильца», идёт через ту же логику, что и вебхук.
- `components/ui/*` — компоненты shadcn/ui (стиль base-nova, на Base UI). Их не пишем руками, а добавляем `npx shadcn add <name>`.

## 5. Сценарии по шагам

### 5.1 Входящее сообщение (`convex/inbound.ts`, `convex/http.ts`)
1. Вебхук `POST /inbound` проверяет `Authorization: Bearer <INBOUND_SECRET>` и формат JSON (иначе 401/400).
2. Вызывает `internal.inbound.receive` → общая функция `receiveMessage`:
   - ищет жильца по email (`by_email`, email приводим к нижнему регистру);
   - берёт его **последнюю** переписку в этом канале (`by_tenant_channel`); если она не закрыта — дописываем туда,
     если закрыта или жилец неизвестен — создаём новую (как новое обращение в поддержку);
   - пишет сообщение, обновляет превью и `lastMessageAt`, ставит статус `open`.
3. Все `useQuery` на фронте получают обновление сами.

### 5.2 Импорт CSV (`convex/imports.ts`, `convex/tenants.ts`, `convex/lib/csv.ts`)
```
фронт: generateUploadUrl() → fetch(POST файл) → storageId → imports.start({storageId})
сервер: start  = mutation: создаёт запись imports(status=running) + scheduler.runAfter(0, imports.run)
        run    = action:   читает файл из storage → parseCsv → toTenantRows
                           → для каждых 200 строк runMutation(tenants.insertBatch)
                           → update(status=done) ; при ошибке status=failed ; в конце удаляет файл
        insertBatch = internalMutation: создаёт дом/квартиру при первом упоминании,
                           пропускает жильца, если email уже есть, увеличивает processed/created/skipped
```
Почему так:
- файл не передаётся аргументом (лимиты на размер), а кладётся в **file storage**;
- разбор в **action**, потому что одна мутация ограничена по времени и объёму;
- **пачки по 200** — каждая отдельная транзакция: упало на середине — сделанное сохранилось,
  а повторный импорт просто пропустит уже добавленных (дедуп по email) → импорт **идемпотентный**;
- прогресс не надо «поллить» — фронт подписан на `imports.latest`.

Парсер CSV свой (≈40 строк): кавычки, `""` внутри кавычек, переносы строк в полях, CRLF, автоопределение `,`/`;`.

### 5.3 AI-агент (`convex/agent.ts`)
1. Кнопка «Let the agent handle it» → mutation `agent.start`: создаёт `agentRuns(status=running)` и ставит
   `agent.run` в scheduler. Кнопка блокируется, пока run `running` — это видно из реактивного `lastRun`.
2. `agent.run` (action):
   - берёт переписку и жильца через `internal.conversations.forAgent`;
   - собирает промпт: системная роль + переписка **в разделителях как данные** (защита от prompt injection
     в письме жильца);
   - цикл до 6 ходов: запрос в OpenRouter (`/chat/completions`, формат OpenAI с `tools`) → если модель вызвала
     инструменты, выполняем их и возвращаем результат как сообщение `role: "tool"` → снова к модели;
   - когда модель ответила текстом без инструментов — это черновик ответа, сохраняем как сообщение `author: "ai"`.
3. Инструменты: `find_tenant` (поиск по индексу/email), `link_tenant` (проверка id через `ctx.db.normalizeId`),
   `create_ticket`, `set_status`. Ошибки инструментов **не роняют** run — текст ошибки уходит модели, она
   может исправиться.
4. Каждый вызов инструмента пишется в `agentRuns.steps` → на фронте видно бейджи шагов в реальном времени.
5. Нет ключа / ответ не 200 / 6 ходов без ответа → `status=failed` с понятной ошибкой в интерфейсе.

Ключ и модель — переменные окружения Convex: `npx convex env set OPENROUTER_API_KEY ...`
(в коде `process.env`, на фронт ключ не попадает).

## 6. Тесты (`convex/*.test.ts`)
`convex-test` поднимает **in-memory** Convex прямо в Vitest — реальные функции, реальная схема, без сети.
- `csv.test.ts` — парсер и маппинг заголовков.
- `backend.test.ts`:
  - импорт: файл в storage → scheduler → итог; повторный импорт = 0 созданных, 2 пропущенных;
  - входящие: сопоставление по email, склейка в одну ветку, другой канал = новая ветка, после `closed` = новая ветка;
  - ответ менеджера → статус `pending`;
  - заявки: создание, доска, перемещение между колонками;
  - жильцы: пагинация и полнотекстовый поиск;
  - агент: `fetch` к OpenRouter подменён — проверяем весь цикл инструментов, что результаты инструментов
    возвращаются модели, обработку плохого id и отсутствие ключа.

`vi.useFakeTimers()` + `t.finishAllScheduledFunctions(vi.runAllTimers)` — так в тесте «прокручиваем» scheduler.

CI (`.github/workflows/ci.yml`) на каждый push: typecheck → lint → tests → build.

npm install

  и переменной `CONVEX_DEPLOY_KEY` из дашборда Convex.

## 8. Что сказать на собеседовании (и что честно признать)

Сильные места:
- реактивность без ручной синхронизации; оптимистичные обновления;
- правильное разделение query / mutation / action и internal-функций;
- идемпотентный пакетный импорт через storage + scheduler;
- агент с инструментами, логом шагов и защитой от prompt injection;
- индексы под каждый сценарий, полнотекстовый поиск, пагинация;
- тесты бэкенда на convex-test и CI.

Что упрощено (и как бы делал в проде):
- **нет авторизации** — добавил бы Convex Auth / Clerk и проверку `ctx.auth` в каждой функции;
- **нет мульти-тенантности** — в реальном продукте у каждой управляющей компании свой `orgId` во всех таблицах и индексах;
- `conversations.counts` считает до 1000 на статус — в проде держал бы счётчики в отдельной таблице или
  использовал компонент агрегатов Convex;
- черновик агента сохраняется как сообщение — в проде отдельное поле «черновик», чтобы его нельзя было спутать с отправленным;
- вебхук принимает упрощённый JSON — для реальных провайдеров (Twilio, Vonage, почта) нужна проверка их подписи и маппинг формата;
- агент не тестировался на реальной модели в CI (там мок) — вручную проверить с ключом перед демо.
